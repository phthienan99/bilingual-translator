A lecture moves fast.
Understanding should keep up.

Building a classroom caption tool that pairs spoken English with Chinese or Vietnamese translation.

The problem

When you are learning in a second language, one unfamiliar phrase can make the next sentence harder to follow. Our prototype keeps English and translated captions together so students can check the original wording while following the lecture.

The first version ran on an Apple Silicon Mac. We then packaged the processing pipeline for Docker Desktop and tested the published image with peers on both Intel and Apple Silicon Macs.

From speech to a readable caption

🎙 Browser microphone → speech detection → English transcription → careful review → translation → paired captions

The app produces early captions while speech continues, then reviews a completed segment. Short captions arrive sooner, but unfinished phrases give the translator less context. Final review can improve punctuation while preserving the recognized words; it also adds work and delay.

Protecting meaning matters more than fluent rewrites

A language model can make an incorrect sentence sound convincing. Our original pipeline rejects many proposed word changes, protecting numbers, names and the words the recognizer actually heard. The current CPU default uses a small model for conservative English review and dedicated models for both translations.

Moving beyond our own laptop

We separated the caption logic from the desktop window. The browser interface records audio and displays results; Docker packages the processing service. Peers used Docker Desktop to pull and run the published image, then opened localhost in their browser.

The original Apple-specific inference runtime was replaced with CPU-compatible adapters. That improves portability but changes speed, memory use and potentially output. The published Docker image now provides both linux/amd64 and linux/arm64 variants. Peer testing covered an Intel Mac, an Apple Silicon Mac with Chrome, and an Apple Silicon Mac with Safari.

AI assistance helped extract the pipeline, create the browser/container adaptation and draft documentation. We must review and test that work rather than assuming generated code is a finished product.

What we measured in the CPU version

The initial large-model configuration took about 25–27 seconds to review and translate one short sentence. A smaller review model and quantized translation engines reduced that cost substantially.

In a short recording replay, the current default produced a first provisional caption about 2.8–3.2 seconds after the server detected speech, with peak process memory around 2.9 GiB. Final captions arrived later. These are measurements from one Mac and one short clip, not a guarantee of classroom accuracy or microphone-to-screen speed.

Testing also caught two useful failures: noise prompted an invented sentence, and a sentence splitter detached “Dr.” from a name. We added a no-speech filter and kept short translation inputs intact. The validation record documents remaining limitations.

What the earlier classroom test taught us

The supplied September 11 desktop test analysis reports 100 final captions from 102 speech segments. It notes technical vocabulary errors and two short mathematical fragments that remained provisional. These are historical observations from the original application, not new Docker results or independent peer feedback.

The lesson is practical: fast captions are useful only when we also show their limits. Terminology and short fragments remain important test cases.
